## v1.9에서 달라진 점

강사 피드백(11/24)으로 Orchestrator 큐를 뺐다. 이전 판에서 바뀐 내용은 13장에 있다.

- ③ 봇은 서버 저장까지만 한다. 큐에 추가하지 않는다(4.2, 4.3, FR-S09, FR-S10).
- ④ 봇은 큐 신호를 기다리지 않는다. Orchestrator 시간 트리거로 1분마다 실행되어 엑셀을 다시 만든다(FR-R01, FR-R07, FR-R11). 직접 실행해도 된다.
- 큐 항목 계약(7.3)을 없앴다. ③과 ④ 사이에 주고받는 데이터는 없고, 둘 다 서버만 본다.
- ④의 실패는 큐 항목이 아니라 Job 상태(Faulted)로 남는다(FR-R06).
- 웹에서 고치거나 지운 내용도 다음 주기에 엑셀에 반영되므로 `in_ForceRefresh` 인자를 없앴다(FR-R10).
- 서버 API 1~12, 결과 JSON(7.1), 엑셀 12열(7.5), 지표 정의(8장)는 바뀌지 않았다.
- 11/24 현재 Orchestrator에는 큐와 큐 트리거가 아직 남아 있다. ③이 큐 추가 단계를 뺀 뒤에 지우고, 시간 트리거를 건다.

## 1. 배경과 목표

고객사 전화 응대 담당자 3명이 통화가 끝난 뒤 이력을 손으로 정리한다. 기억에 의존해 기록이 빠지고, 통화마다 유형 분류·요약·조치 정리·엑셀 입력을 반복하며, 엑셀에 행으로만 쌓여 추이를 보기 어렵다. [개요]

이 제품은 통화 녹취 파일을 넣으면 아래가 자동으로 끝나게 한다.

| 목표 | 내용 |
|---|---|
| 후처리 자동화 | 음성에서 5대 유형(질의, 불만, 건의, 교육 내용, 기타 문의), 질문 요지, 조치 내역을 뽑는다. |
| 기록의 일관성 | 표준 형식으로 DB와 엑셀에 적재한다. |
| 결과물 이원화 | 내부 보고용 엑셀 대시보드와 실시간 조회용 웹 대시보드를 함께 제공한다. |

### 4.2 흐름 A — 폴더의 음성을 처리해 결과를 한 번에 저장 (P0, MVP)

| 순서 | 누가 | 하는 일 |
|---|---|---|
| 1 | 봇 (③) | 음성 폴더의 파일을 읽고 SHA-256(`file_hash`)을 계산한다. 파일명에서 통화일시·담당자·고객사를 얻는다. 수동이나 일정으로 실행한다. |
| 2 | 봇 (③) | STT → 화자 정제 → 마스킹 → 분류·요약 → 검증 |
| 3 | 봇 (③) | `POST /api/calls`(API 1)를 한 번 부른다. 중간에 실패한 통화도 같은 API로 실패를 저장한다. |
| 4 | 서버 (①) | 검증, 값 보정, 중복 확인 후 저장하고 관리번호(`call_id`)를 돌려준다. |
| 5 | 봇 (③) | 409(이미 저장된 파일)는 건너뛰고, 422(입력 오류)는 로그를 남기고 다음 파일로 간다. 처리한 음성은 입력 폴더에서 `done/`(201, 409) 또는 `failed/`(실패로 저장됨, 422)로 옮긴다. |
| 6 | 봇 (④) | 시간 트리거로 1분마다 실행되어 서버 목록(API 2)으로 엑셀 통화 대장을 다시 쓴다. 요약·대시보드 시트는 수식으로 따라온다. |
| 7 | 웹 (②) | API 6(통계)과 API 2(목록)로 화면을 그리고, 행을 누르면 API 3·4·5를 쓴다. |

### 4.3 흐름 B — 웹에서 올린 음성을 처리 (P1, Job 시작은 P2)

| 순서 | 누가 | 하는 일 |
|---|---|---|
| 1 | 웹 | `POST /api/recordings`(API 9)로 음성을 올린다. 서버가 저장하고 `RECEIVED` 행을 만든다. 통화일시·담당자·고객사·해시는 서버가 갖는다. |
| 2 | 서버 또는 봇 | 처리를 시작한다. (가) 서버가 Orchestrator Job을 시작한다(API 12, 인자 3개는 7.4). (나) 봇이 `GET /api/calls?status=RECEIVED`로 대기 건을 찾아 API 12를 부른다("가져가기"). `ORCH_ENABLED=false`이면 API 12는 Job을 만들지 않고 상태만 `PROCESSING`으로 바꾼다. 이미 다른 봇이 가져갔으면 409다. |
| 3 | 봇 (③) | `GET /api/calls/{id}/audio`(API 10)로 음성을 받아 STT·분석을 한다. |
| 4 | 봇 (③) | `PUT /api/calls/{id}/result`(API 11)로 결과나 실패 사유를 저장한다. |
| 5 | 서버 (①) | 30분 넘게 결과가 없는 통화를 `FAILED`(`TIMEOUT`)로 바꾼다. Job 상태는 조회하지 않는다. |
| 6 | 봇 (④) | 흐름 A의 6번과 같다. |

시연 기본값은 (나) 가져가기다(`ORCH_ENABLED=false`). ③ 봇이 주기적으로 대기 건을 확인한다. 음성을 올리는 것만으로는 처리가 시작되지 않는다(업로드 직후 자동으로 시작하던 설정 `ORCH_AUTO_START`는 서버에서 없앴다). Orchestrator 환경은 확인됐다(4.1). (가)로 바꾸려면 외부 앱의 Client ID와 Secret, ③ 프로세스의 키, 무인 실행 설정이 있어야 한다(11장 30·31번). 수요일 오전 Job 시작 시험에 성공하면 `ORCH_ENABLED`를 `true`로 바꿔 (가)로 전환하며, 수 12:00에 하나로 고정한다. API 12를 부르는 쪽은 방식마다 하나다. (가)에서는 웹이 부른다. 업로드 뒤 자동으로 부르지 않고, "처리 시작" 버튼을 사용자가 누를 때 부른다. 버튼은 `GET /health`의 `orchestrator.enabled`가 `true`일 때만 보인다. 이때 ③ 봇은 API 12를 부르지 않고 Job 인자로 음성 주소를 받아 처리한 뒤 결과만 저장한다(API 11). (나)에서는 ③ 봇만 부르고 웹은 부르지 않는다. Webhook은 쓰지 않는다. 웹은 P0·P1에서 "대기" 상태만 표시하고 처리 시작 버튼(P2)은 두지 않는다. [답변] [팀 결정]

### 4.4 처리 상태

| 서버 값 | 화면 표시 | 뜻 | 다음 상태 |
|---|---|---|---|
| `RECEIVED` | 대기 | 음성이 저장됐고 처리 전이다. | `PROCESSING` |
| `PROCESSING` | 처리 중 | 봇이 처리하고 있다. | `DONE`, `FAILED` |
| `DONE` | 완료 | 분석 결과가 저장됐다. 끝 상태다. | 없음 |
| `FAILED` | 실패 | 사유(`코드: 설명`)와 함께 저장됐다. 다시 시작할 수 있다. | `RECEIVED`, `PROCESSING` |

흐름 A로 들어온 통화는 `RECEIVED`와 `PROCESSING`을 거치지 않고 바로 `DONE`이나 `FAILED`가 된다. 통계와 엑셀은 `DONE`만 센다. [백엔드 PRD]

가져가기 방식에서 실패(`FAILED`)한 통화는 ③ 봇의 대기 목록(`status=RECEIVED`)에 나오지 않는다. 다시 처리하려면 같은 파일을 다시 올린다. 서버가 그 행을 `RECEIVED`로 되돌린다(민영, [백엔드 PRD] 인수 테스트 10번). 웹에서 삭제한 뒤 다시 올려도 된다(범수). [팀 결정]

**대장을 서버 목록으로 만드는 이유**: 서버가 보정한 값(7.2)과 웹에서 수정·삭제한 내용은 서버에만 있다. 그래서 대장의 값은 전부 서버에서 받고, 매번 완료 통화 전체로 다시 만든다. 한 번 실패해도 다음 실행 때 전체를 다시 받으므로 빠지는 통화가 없다.

**실행 방식**: Orchestrator 시간 트리거로 1분마다 무인 실행한다. Studio, Assistant, Orchestrator의 Start Job으로 직접 실행해도 된다. 무인 실행 자리가 1개라 ③의 Job 시작을 시험할 때는 시간 트리거를 잠깐 끈다.

**엑셀은 엑셀 프로그램으로 템플릿을 열어 쓴다.** 파일을 새로 만들어 내는 방식은 차트와 슬라이서를 잃을 수 있다. 봇 PC에 엑셀이 있어야 한다.

## 7. 데이터 계약

### 7.1 결과 JSON (③ → ① 서버)

③의 결과 JSON은 서버 API 요청 본문과 같은 필드 이름을 쓴다. 흐름 A에서는 그대로 API 1의 본문이 되고, 흐름 B에서는 "흐름 B" 열이 "생략"인 항목을 뺀 나머지가 API 11의 본문이 된다. [STT]

| 필드 | 값과 출처 | 규칙 | 흐름 B |
|---|---|---|---|
| `called_at` | 파일명. 없으면 파일 수정 시각 | 필수. `2026-11-23T10:15:00+09:00` 형식 | 생략 |
| `agent_name` | 파일명. 읽지 못하면 `미확인` | 필수. 내부 직원이라 마스킹하지 않는다. | 생략 |
| `customer_company` | 파일명. 읽지 못하면 `미확인` | | 생략 |
| `customer_phone` | 대화에서 확인되면 | 마스킹 형태 `010-****-1234`. 없으면 `null` | 보냄 |
| `source_filename` | 원본 음성 파일명 | 필수 | 생략 |
| `file_hash` | 음성 바이트의 SHA-256 | 필수. 소문자 16진수 64자. 중복 판단 기준 | 생략 |
| `transcript` | 화자 정제와 마스킹의 결과 | `[상담원] …` / `[고객] …` 줄. | 보냄 |
| `category` | GenAI | 질의 / 불만 / 건의 / 교육 내용 / 기타 문의 | 보냄 |
| `customer_question` | GenAI(문의·불만 요지) | 줄바꿈 없이 200자 이내 | 보냄 |
| `action_taken` | GenAI(담당자 조치 내역) | 줄바꿈 없이 200자 이내 | 보냄 |
| `follow_up_needed` | GenAI | `true`/`false`. 실패 시 보내지 않는다. | 보냄 |
| `confidence` | CLOVA 응답의 전체 confidence | 0~1. 음성 인식 신뢰도이며 분류가 맞았는지를 나타내지 않는다. 서버가 소수 둘째 자리로 저장한다. | 보냄 |
| `analysis_json` | GenAI 응답 원본 | JSON 객체. `customer_name`(`김○○`, 없으면 `null`)과 `duration_sec`을 여기에 담는다. | 보냄 |
| `status` | `DONE` / `FAILED` | 서버 상태값과 같다. | 보냄 |
| `error_message` | 실패 시 `코드: 사유`(API 1은 없으면 422) | 성공 시 `null` | 보냄 |
| `call_id` | 서버가 발급 | 보내지 않는다. API 1 응답이나 Job 인자로 받는다. | 해당 없음 |

실패해도 결과는 반드시 저장한다. 흐름 A의 실패 건은 필수 4개(`called_at`, `agent_name`, `source_filename`, `file_hash`)와 `status=FAILED`, `error_message`를 보낸다. 파일명에서 고객사를 읽었으면 `customer_company`도 보낸다. 같은 파일을 다시 처리해 성공하면 서버가 같은 `call_id`로 덮어쓴다(`retry_count` +1).

### 7.2 서버가 저장하면서 바꾸는 값 ([백엔드 PRD] FR-B01)

| 규칙 | 결과 |
|---|---|
| 필수 4개가 없거나 `called_at`에 시간대가 없다. | 422 |
| 같은 `file_hash`가 완료(`DONE`)이거나 처리 중이다. | 409 `DUPLICATE_FILE` |
| 같은 `file_hash`가 실패(`FAILED`)다. | 같은 관리번호로 덮어쓴다. |
| 담당자·고객사 이름에 앞뒤 공백이 있다. | 지운다. |
| 유형이 5개 값에 없다. | `기타 문의`로 바꾸고 `needs_review=true` |
| `confidence`가 없거나 0.7 미만이다. | `needs_review=true` |
| 완료인데 `follow_up_needed`, `needs_review`가 없다. | `false`로 채운다. |
| 연락처와 대화에 전화번호, 주민등록번호 형태, 이메일이 있다. | 마스킹해서 저장한다. |

따라서 서버에 저장된 값은 봇이 보낸 값과 다를 수 있다. 웹과 엑셀은 서버에 저장된 값을 쓴다.

### 7.3 큐 항목 (삭제)

v2.0에서 없앴다. 강사 피드백(11/24)으로 Orchestrator 큐를 쓰지 않는다. ③과 ④ 사이에 주고받는 데이터는 없다. ③은 서버에 저장하고(7.1), ④는 서버 목록(API 2)을 읽는다. 절 번호는 다시 매기지 않는다.

### 7.4 공통 값

**Job 입력 인자(흐름 B)**: ③ 워크플로우 `Main.xaml`의 In 인자 이름이다. 가져가기 방식에서는 인자 없이 실행되고 봇이 `call_id`로 주소를 만든다. [STT] [백엔드 설계]

### 7.5 엑셀 통화 대장

통화 1건이 DB 1행이고 엑셀 1행이다. 대장에는 완료된 통화만 들어간다. [백엔드 MVP]

엑셀 파일은 두 종류다. 통화 대장 12열의 열 순서와 변환 규칙은 두 파일이 같다.

| 파일 | 만드는 곳 | 내용 | 받는 방법 |
|---|---|---|---|
| `콜센터_통화목록_YYYYMMDD.xlsx` | 서버(API 7) | 12열 통화 목록 한 시트. 웹의 검색 조건이 적용된다. | 웹의 "엑셀 다운로드" 버튼 |
| `콜센터_엑셀_최신.xlsx` | ④ 봇 | 대시보드·요약·통화 대장·안내 4시트. 완료 통화 전체 | ④가 직접 전달 |

| 열 | 항목 | 서버 항목 | 쓰는 규칙 |
|---|---|---|---|
| A | 관리번호 | `call_id` | |
| B | 통화일시 | `called_at` | 한국 시간으로 바꾼 뒤 엑셀 날짜로 쓴다. 문자열로 쓰면 일별 추이가 전부 0이 된다. |
| C | 담당자 | `agent_name` | |
| D | 고객사 | `customer_company` | |
| E | 연락처 | `customer_phone` | 마스킹된 값. 대화에서 확인되지 않으면 빈칸이다. |
| F | 유형 | `category` | 5개 값 그대로 |
| G | 고객 질문 요지 | `customer_question` | |
| H | 담당자 조치 내역 | `action_taken` | |
| I | 후속조치 | `follow_up_needed` | `true`/`false`를 `Y`/`N`으로 |
| J | AI 결과 검토 필요 | `needs_review` | 서버가 판정한 값. `true`/`false`를 `Y`/`N`으로 |
| K | 녹취 파일명 | `source_filename` | |
| L | 통화 내용(숨김) | `transcript` | 32,000자에서 자른다. |

- 12개 열은 서버 목록 `GET /api/calls?status=DONE&include_transcript=true&size=200` 응답으로 모두 채울 수 있다(① 확인). `page`를 올려 가며 받고, 응답의 `total`로 마지막 쪽을 안다.
- 목록은 최신순(`called_at` 내림차순)으로 온다. ④ 봇은 통화일시 오름차순으로 정렬해 쓴다 **(제안)**.
- 웹에서 수정·삭제한 내용은 봇이 다음에 대장을 만들 때 엑셀에 반영된다.
- 담당자나 고객사가 `미확인`인 통화도 그대로 넣는다. 담당자별 집계에 `미확인`이 한 줄 생기며, 웹의 통계도 같다.
- 대장을 다시 쓸 때는 데이터 행(`A2:L1000`)의 값만 지우고 채운다. 시트나 행을 지우면 요약 시트의 수식, 목록 제한, 조건부 서식이 깨진다. 쓴 뒤 표 `tblCalls`의 범위를 데이터 행 수에 맞춘다.
- 원본 템플릿은 요약 시트의 담당자(3명), 통화일(4일), 고객사(5곳) 목록과 차트 범위가 고정이었다. 템플릿 v3은 세 목록을 수식으로 만들고 차트가 값이 있는 행까지만 그리므로, 봇은 요약 시트를 건드리지 않는다. 담당자 10명, 날짜 14일, 고객사 10곳을 넘으면 넘는 만큼은 블록에 나오지 않는다. [엑셀] [RPA]
- 요약 시트의 수식은 1,000행(999건)까지만 센다. 넘으면 최신 999건만 쓰고 경고를 남긴다 **(제안)**.
- 엑셀에 새 열이 필요하면 서버 항목으로 만들 수 있는지 먼저 보고, 안 되면 백엔드 두 사람에게 알린다.

## 8. 지표 정의 (웹과 엑셀이 같은 정의를 쓴다)

| 카드 | 계산 |
|---|---|
| 분석된 통화 | 완료(`DONE`) 건수. 실패와 처리 중은 뺀다. |
| 후속조치 필요 | 완료 건 중 `follow_up_needed`가 참인 건수 |
| AI 결과 검토 필요 | 완료 건 중 `needs_review`가 참인 건수 |
| 불만 통화 | 유형이 `불만`인 건수 |
| 불만 비율 | 불만 통화 ÷ 분석된 통화. 분석된 통화가 0이면 0%. 정수로 반올림해 표시한다(3/14는 21%). |
| 가장 많은 유형 | 건수가 가장 큰 유형. 동률이면 고정 순서(질의, 불만, 건의, 교육 내용, 기타 문의)에서 앞선 유형 |

| 차트 | 데이터 | 형태 |
|---|---|---|
| 유형별 건수 | 유형 5개(0건이어도 표시) | 막대 |
| 일자별 유형 추이 | 날짜별 유형 건수 | 누적 막대 |
| 담당자별 통화·후속조치 | 담당자별 통화 건수와 후속조치 건수 | 막대 2개 |
| 고객사별 불만 건수 | 불만이 많은 순 상위 10곳. 엑셀은 불만 건수가 같으면 통화가 많은 순으로 놓는다. 웹과 같은지 확인한다(11장 33번). | 가로 막대 |

- 웹과 엑셀은 "분석된 통화"(완료 건, seed 기준 14)를 기준으로 쓴다. 서버의 `total_calls`(실패와 처리 중을 포함한 전체, seed 기준 15)와 다른 값이므로 엑셀에서 "총 통화"라는 이름을 쓰지 않는다.
- "검토 필요"는 서버가 판정한다. `confidence`가 없거나 0.7 미만일 때, 그리고 유형을 보정했을 때 표시한다. 기준 0.7은 임시값이며 화 12:00 첫 연동에서 실제 값을 보고 한 번만 조정한다.
- `confidence`는 음성 인식 신뢰도다. 화면에는 "음성 인식 신뢰도"로 표시한다. 분류 결과의 신뢰도는 따로 내지 않는다.

- 엑셀 템플릿의 지표 이름, 불만 비율의 정수 표시, 동률 규칙은 위 정의와 같다. seed 14건을 템플릿에 넣어 확인했다(10장). [RPA]
